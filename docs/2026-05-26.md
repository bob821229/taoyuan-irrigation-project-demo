新增提問回覆

    1. API 改用 POST + JSON payload

        同意，正式產品建議統一使用 POST，payload 傳 JSON object。這樣未來查詢條件變多時，不需要一直調整 URL 結構，也比較容易帶入使用者權限、時間範圍、圖層條件、資料版本、行政區篩選等參數。

        原本規劃中的 GET API 建議調整為：

            POST /api/irrigation/node/children
            POST /api/irrigation/branch/overview
            POST /api/irrigation/node/detail

        payload 基本格式：

            {
              "nodeId": "branch__03009001",
              "type": "branch",
              "code": "03009001"
            }

    2. 第三層進畫面時完整取得資料

        同意，第三層建議進畫面時一次取得完整資料。第三層的 hover、圖例底色、畫面數值標籤、彈窗摘要，都應優先從這份完整資料中 filter，不應該 hover 一次打一支 API。

        進第三層時呼叫：

            POST /api/irrigation/branch/overview

        payload：

            {
              "branchId": "branch__03009001",
              "include": ["groups", "ponds", "sensors", "weirs", "cctvs"],
              "time": "latest"
            }

        回來後前端建立 byId map，例如 groupsById、pondsById、sensorsById。hover 或 click 時只用 id 從 map 取資料。

        如果彈窗只是顯示 overview 已有的摘要資料，就直接從 overview filter；如果彈窗未來包含大量歷史表格、趨勢圖、維護紀錄，再點 __info 時用 POST detail API 補查詳細資料。

    3. 前兩層是否只有 __nav 跟 __info

        是，前兩層建議只明確處理 __nav 與 __info。

        前兩層主要負責層級導覽與區塊資訊彈窗，不需要像第三層一樣做大量圖例套色與即時數值標籤，所以互動規則可以保持單純：

            stn__03009001__nav：進入下一層。
            stn__03009001__info：開啟彈窗。
            branch__03009001__nav：進入下一層。
            branch__03009001__info：開啟彈窗。

        如果設計圖上保留 stn__03009001 或 branch__03009001 這類本體 id，前兩層可以把它視為資料節點或 hover 樣式參考，但不建議預設點擊本體就開彈窗。正式產品最好讓 icon 或明確熱區處理互動，避免使用者誤點大面積區塊。

    4. SVG 進頁面後是否先做一次處理

        建議要做，而且這會是正式產品可維護性的關鍵。

        SVG raw HTML 插入畫面後，前端應跑一次 normalizeSvgElements，把符合命名規則的 element 補上 data-* metadata，例如：

            id="branch__03009001__info"
            data-node-id="branch__03009001"
            data-type="branch"
            data-code="03009001"
            data-action="info"
            data-interactive="true"

        對無後綴資料節點：

            id="pond__03009001"
            data-node-id="pond__03009001"
            data-type="pond"
            data-code="03009001"
            data-action="data"
            data-bindable="true"

        這樣後續操作可以統一靠 data-*：

            click 找最近的 [data-interactive="true"]。
            hover 找最近的 [data-type="pond"], [data-type="sensor"]。
            圖例套色找 [data-node-id="group__03009002"]。

        id 仍然要保留，因為它是 SVG 與 API 資料對應的穩定 key；data-* 是前端正規化後方便操作的 metadata，不應取代 id。

規劃建議

    1. SVG id 命名原則

        建議把 id 拆成「資料節點」與「互動熱區」兩種概念，不要只靠有沒有 _door 判斷所有行為。

        建議格式：

            {type}__{code}
            {type}__{code}__nav
            {type}__{code}__info

        範例：

            stn__03009001
            stn__03009001__nav
            stn__03009001__info
            branch__03009001
            branch__03009001__nav
            branch__03009001__info
            pond__03009001
            sensor__03009001
            group__03009002

        說明：

            type：資料類型，例如 stn、branch、pond、sensor、group、weir、cctv。
            code：業務代碼，保留原始系統或資料庫可查詢的代碼。
            __nav：點擊後進入下一層。
            __info：點擊後開啟彈窗。
            沒有後綴的 id：代表這是資料節點本身，可用於著色、標籤定位、資料綁定，不直接推定互動行為。

        不建議繼續使用 _door 作為正式產品規格，因為 door 是視覺或設計稿語意，不是產品互動語意。正式產品建議改成 __nav，比較清楚表示這個區塊會導頁。

        i icon 開彈窗的部分建議加上 __info 後綴。原因是同一個資料節點可能同時需要：

            點區塊本體：選取、套用圖例色、顯示數值。
            點進入符號：進下一層。
            點資訊符號：開詳細彈窗。

        如果資訊 icon 沒有 __info 後綴，前端很難穩定判斷「這次點擊是要看資料，還是只是點到資料區塊本體」。

    2. 正式產品互動規則

        建議將 SVG 互動規則定義成資料表或設定檔，不要在每一層 Vue component 裡硬寫 selector。

        每個 SVG element id 都先解析成：

            rawId: branch__03009001__info
            type: branch
            code: 03009001
            action: info
            payloadId: branch__03009001

        action 規則：

            __nav：導向下一層，並把 payloadId 當作下一層查詢參數。
            __info：打 detail API，開啟詳細彈窗。
            無後綴：預設不開彈窗、不導頁，只作為資料綁定或 hover 目標。

        hover 規則：

            pond、sensor 這類即時資訊點，可以 hover 顯示 tooltip。
            group、branch、stn 這類較大的管理區塊，不建議 hover 打 API，避免滑鼠移動造成大量請求。

        click 規則：

            nav 類型只負責導頁。
            info 類型只負責開彈窗。
            如果未來真的需要「點資料區塊本體也開彈窗」，也應該由設定檔明確定義 clickable: true，而不是靠命名猜測。

    3. API 呼叫時機

        第一層、第二層：

            進入畫面時只需要載入該層 SVG 與基本頁面資料。
            點 __info 時才呼叫 detail API，使用 POST + JSON payload。
            點 __nav 時導頁，並把目前節點 payloadId 傳給下一層。

        第三層：

            建議進入畫面時就呼叫 overview API，使用 POST + JSON payload，例如：

                POST /api/irrigation/branch/overview

            以目前案例來說，進第三層時帶：

                {
                  "branchId": "branch__03009001",
                  "include": ["groups", "ponds", "sensors", "weirs", "cctvs"],
                  "time": "latest"
                }

            API 回傳這條支線底下所有畫面需要的資料，例如：

                groups：水利小組與作物期資料，用來套圖例底色。
                ponds：埤塘有效水量、百分比、時間、單位，用來顯示畫面數值與 hover tooltip。
                sensors：感應器流量、水位、時間，用來顯示畫面數值與 hover tooltip。
                weirs：河水堰資料。
                cctvs：影像點位資料。

            這樣第三層不需要每個 pond 或 sensor 各打一支 API 才能顯示畫面上的數值。畫面載入後可以直接把 overview response 建立成 byId map，後續 hover、彈窗、圖例底色都從本地資料 filter。

        tooltip API 策略：

            第三層 tooltip 顯示的資料應包含在 overview response，hover 時不要再打 API。
            如果未來 tooltip 需要非常即時的資料，應由 overview API 支援重新整理，或由畫面提供手動刷新，不建議滑鼠 hover 直接觸發網路請求。

        detail API 策略：

            使用者點 __info 或設定為 clickable 的節點時才呼叫：

                POST /api/irrigation/node/detail

            payload 使用 payloadId，例如：

                {
                  "nodeId": "branch__03009001",
                  "type": "branch",
                  "code": "03009001"
                }

            第三層如果 overview 已包含彈窗所需資料，點 __info 時可以不打 detail API，直接從 overview byId map 取資料。

    4. 建議 API 規格

        層級導覽 API：

            POST /api/irrigation/node/children

        payload：

            {
              "nodeId": "stn__03009001",
              "type": "stn",
              "code": "03009001"
            }

        用途：

            查詢某節點下一層有哪些資料與可用圖層。

        第三層總覽 API：

            POST /api/irrigation/branch/overview

        payload：

            {
              "branchId": "branch__03009001",
              "include": ["groups", "ponds", "sensors", "weirs", "cctvs"],
              "time": "latest"
            }

        回傳範例：

            {
              "branchId": "branch__03009001",
              "groups": [
                {
                  "id": "group__03009002",
                  "cropStage": "paddy",
                  "area": 33.31
                }
              ],
              "ponds": [
                {
                  "id": "pond__03009001",
                  "storage": 3.78,
                  "maxStorage": 6.67,
                  "percent": 57,
                  "unit": "萬噸",
                  "time": "115/05/15 16:00"
                }
              ],
              "sensors": [
                {
                  "id": "sensor__03009001",
                  "flow": 0.5,
                  "flowUnit": "cms",
                  "waterLevel": 0.8,
                  "waterLevelUnit": "m",
                  "time": "115/05/15 16:00"
                }
              ]
            }

        詳細彈窗 API：

            POST /api/irrigation/node/detail

        payload：

            {
              "nodeId": "group__03009002",
              "type": "group",
              "code": "03009002"
            }

        用途：

            回傳彈窗 tabs、summary、table 等內容。

    5. 前端共用邏輯建議

        建議抽出 composable：

            useSvgInteraction()

        負責：

            parseSvgElementId(rawId)
            normalizeSvgElements(svgRoot)
            getInteractiveTarget(event)
            resolveAction(parsedId)
            handleNav(payloadId)
            handleInfo(payloadId)
            handleHover(payloadId)

        normalizeSvgElements(svgRoot) 負責在 SVG 插入畫面後，替符合命名規則的 element 補上：

            data-node-id
            data-type
            data-code
            data-action
            data-interactive
            data-bindable

        建議抽出資料綁定 composable：

            useMapOverviewData()

        負責：

            進第三層時用 branchId 以 POST 呼叫 overview API。
            建立 byId map，例如 pondsById、sensorsById、groupsById。
            提供 getNodeData(id) 給 tooltip、標籤、圖例著色共用。
            第三層 hover 與彈窗優先從 overview byId map filter，不在互動當下打 API。

        建議抽出圖例樣式 composable：

            useMapLegendStyles()

        負責：

            根據 overview data 和 legend filters 套用 SVG fill。
            控制顯示或隱藏 pond storage、sensor flow 等數值標籤。
            不直接依賴特定 SVG 檔名，只依賴 id 與資料類型。

    6. 後續正式產品落地順序

        第一階段：

            先統一 SVG id 命名規則，設計端或出圖流程固定產生 __nav、__info、資料節點 id。

        第二階段：

            把目前 Vue component 內硬寫的 id 陣列改成通用 parser、normalizeSvgElements 與設定檔。

        第三階段：

            第三層改成進畫面先用 POST 打 branch overview API，畫面數值、tooltip、圖例底色、彈窗摘要都從 overview response 產生。

        第四階段：

            detail 彈窗統一走 node detail API，前端不需要知道 stn、branch、group 的彈窗資料結構差異，只負責渲染 API 回傳的 tabs。

        第五階段：

            如果後續不同管理處、工作站、支線都要套用，只需要更換 SVG 與 route 參數，不需要再為每張圖客製化 click/hover 邏輯。
