建議與計畫

    1. SVG 底圖動態效果

        建議做法：

            不要直接修改原始 SVG 檔案內容來寫動畫，建議由前端在 SVG 載入後，依照 id 或 class 對特定圖層補上 class，再由 CSS 控制動畫。

            原因：

                SVG 之後會持續由設計端或 GIS 出圖流程替換。
                如果直接改 SVG 內部 style，每次換圖都容易遺失動畫設定。
                前端用 id/class 套動畫，維護成本比較低，也比較接近正式產品做法。

        SVG 命名建議：

            河流線段建議在出圖時加入明確前綴，例如：

                river_03009001
                river_03009002
                canal_03009001
                drain_03009001

            如果目前 SVG 底下所有線圖都是河流，但 id 還沒有規則，建議後續請出圖流程補上 river_ 前綴，前端才能穩定辨識。

        流向判斷建議：

            不建議讓前端自行判斷水流方向。SVG 的 path/polyline 雖然有繪製順序，但這個順序不一定等於實際水流方向，尤其 SVG 可能來自 Illustrator、GIS、轉檔工具或人工編修，路徑方向很容易被反轉、合併或重建。

            所以正式產品建議在出圖或後端資料中明確定義方向，而不是靠前端猜。

            建議方式有三種：

                方式一：用 data-flow-dir 或資料表欄位定義方向

                    id="river_03009001"
                    data-flow-dir="forward"

                    或 API 回傳：

                    {
                      "id": "river_03009001",
                      "flowDirection": "forward"
                    }

                    forward 代表依 SVG path 原始方向流動。
                    reverse 代表反向流動。

                方式二：用 id 後綴定義方向

                    river_03009001_fwd
                    river_03009001_rev

                    這種方式簡單，但 id 會把視覺動畫資訊和資料 key 混在一起。若未來 API 要用 river_03009001 當資料 id，還要再拆字串，不如 data-flow-dir 清楚。

                方式三：由後端或 GIS 圖資提供 fromNode / toNode

                    {
                      "id": "river_03009001",
                      "fromNodeId": "node_A",
                      "toNodeId": "node_B"
                    }

                    這是最接近正式水利圖資的方式，但前端仍需要知道 SVG path 的繪製方向是否與 from/to 一致，所以通常還是會需要 flowDirection 或 pathDirectionCorrect 這類欄位。

            最推薦：

                SVG element 保留穩定 id，例如 river_03009001。
                方向放在 data-flow-dir 或 API metadata，不放在 id 裡。
                前端 normalizeSvgElements 時把方向補成 class：

                    data-flow-dir="forward" -> class="is-animated-river is-flow-forward"
                    data-flow-dir="reverse" -> class="is-animated-river is-flow-reverse"

            CSS 範例：

                .is-flow-forward path,
                .is-flow-forward polyline,
                .is-flow-forward line {
                  animation-name: river-flow-forward;
                }

                .is-flow-reverse path,
                .is-flow-reverse polyline,
                .is-flow-reverse line {
                  animation-name: river-flow-reverse;
                }

                @keyframes river-flow-forward {
                  to {
                    stroke-dashoffset: -16;
                  }
                }

                @keyframes river-flow-reverse {
                  to {
                    stroke-dashoffset: 16;
                  }
                }

            如果暫時沒有方向資料：

                可以先全部使用同一方向的動畫，只作為 demo 視覺效果。
                但文件與資料規格要先保留 flowDirection 欄位，避免正式產品時大改。

        前端處理方式：

            SVG 載入後執行 normalizeSvgElements(svgRoot)。
            找出 id 以 river_ 開頭的元素，補上：

                data-type="river"
                class="is-animated-river"

            CSS 使用 stroke-dasharray / stroke-dashoffset 製作流動感：

                .is-animated-river path,
                .is-animated-river polyline,
                .is-animated-river line {
                  stroke-dasharray: 8 8;
                  animation: river-flow 1.2s linear infinite;
                }

                @keyframes river-flow {
                  to {
                    stroke-dashoffset: -16;
                  }
                }

        注意事項：

            動畫只建議套在 river/canal 這類線條，不要套在大量 polygon 或整張圖，避免效能變差。
            如果河流線本身不是 stroke，而是填色 shape，CSS dash 動畫可能不適用，會需要改成 overlay 一條動畫線或請出圖時保留 stroke 線段。
            需要尊重 prefers-reduced-motion，使用者系統設定減少動畫時應關閉流動效果。

        實作計畫：

            第一階段：
                先確認 SVG 內河流線段的 id 命名規則，若沒有規則，請出圖流程補 river_ 或 canal_ 前綴。
                同時確認是否能在出圖流程或 API metadata 中提供 flowDirection。

            第二階段：
                新增 useSvgEffects 或擴充現有 normalizeSvgElements，將 river_ / canal_ 元素補上動畫 class。
                若有 flowDirection，補上 is-flow-forward 或 is-flow-reverse。

            第三階段：
                在 styles.css 補 river-flow-forward、river-flow-reverse 動畫與 prefers-reduced-motion 關閉規則。

            第四階段：
                針對第三層先驗證動畫效果，再套用到第一、二層。

    2. 彈窗新增「影像資訊」分類

        可行性：

            可以。後端只要提供經緯度，前端可以自行組出 Google Maps iframe URL，再放進彈窗的「影像資訊」tab。

        建議不要讓後端直接回傳完整 iframe tag。

        原因：

            iframe tag 屬於前端呈現邏輯，後端只應提供結構化資料。
            如果後端回傳 HTML tag，前端需要處理 XSS 與 sanitize，安全成本較高。
            正式產品較建議後端提供 latitude、longitude、zoom、mapType 等欄位，由前端組 URL。

        後端建議回傳欄位：

            {
              "id": "weir_03009002",
              "location": {
                "latitude": 24.900000,
                "longitude": 121.050000,
                "zoom": 16,
                "mapType": "roadmap"
              }
            }

        前端可組出的 iframe src：

            https://www.google.com/maps?q={latitude},{longitude}&z={zoom}&output=embed

        範例：

            https://www.google.com/maps?q=24.900000,121.050000&z=16&output=embed

        iframe 建議由 Vue component 產生：

            <iframe
              :src="mapEmbedUrl"
              loading="lazy"
              referrerpolicy="no-referrer-when-downgrade"
              allowfullscreen
            ></iframe>

        彈窗資料格式建議：

            在 node detail API 回傳 tabs 時新增 media/map 類型，不要把它塞進原本 summary/table 結構硬做。

            範例：

                {
                  "name": "media",
                  "label": "影像資訊",
                  "layout": "media-map",
                  "map": {
                    "latitude": 24.900000,
                    "longitude": 121.050000,
                    "zoom": 16
                  },
                  "media": [
                    {
                      "type": "image",
                      "title": "現場影像",
                      "url": "/api/media/weir_03009002/latest"
                    }
                  ]
                }

        UI 建議：

            影像資訊 tab 可以採左右 layout：

                左側：Google Map iframe。
                右側：現場影像、CCTV 截圖、設備照片或最新影像列表。

            如果只有地圖，仍保留 tab，但地圖可以滿版顯示。

        Google Maps 注意事項：

            直接用 google.com/maps?q=lat,lng&output=embed 通常可以嵌入，但正式產品若要穩定、可控、商用，需要確認 Google Maps Platform 授權與 API Key 政策。
            若未來要自訂 marker、圖層或互動，建議改用 Google Maps JavaScript API 或 Leaflet/OpenStreetMap，而不是 iframe。

        實作計畫：

            第一階段：
                在 StationDetailDialog 支援新的 tab layout，例如 layout: "media-map"。

            第二階段：
                新增 MapEmbed 元件，負責接收 latitude、longitude、zoom 並組 iframe src。

            第三階段：
                在感應器、埤塘、河水堰的 mock data 補上「影像資訊」tab。

            第四階段：
                未來接正式 API 時，後端只回傳 location / media 結構，前端維持同一套渲染邏輯。

    3. 建議優先順序

        第一優先：
            先做「影像資訊」tab，因為它會影響 API response schema 與彈窗共用元件。

        第二優先：
            再定義 SVG 動態效果的命名與流向 metadata，至少要確認 river_/canal_ 前綴與 flowDirection 欄位。

        第三優先：
            把 SVG normalize 流程整理成共用工具，之後同時支援 data-* metadata、info tooltip、river animation。

        第四優先：
            實作 river-flow-forward / river-flow-reverse 動畫，先套用在第三層確認效果，再擴展到其他層。
